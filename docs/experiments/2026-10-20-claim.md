# Plex server claim experiment — 2026-10-20

## Procedure

- Used the previously authenticated PlexBridge client identity and account token.
- Requested one short-lived claim token from `plex.tv`.
- Sent one `POST` claim exchange to `https://plex.tv/api/claim/exchange?token=...` with Plex Media Server identity headers.
- Polled the authenticated account resource list three times.

Secrets and raw responses were intentionally not recorded.

## Result

- Claim exchange HTTP status: `200`
- Server token returned: yes
- PlexBridge resource match: no
- Account resource count after the exchange: `1`
- The only returned server resource was an existing shared server, not PlexBridge.

## Interpretation

The claim endpoint accepted the short-lived token and returned a server token, but that is not sufficient evidence of account registration. Plex did not publish a resource whose identifier matched PlexBridge's persistent machine identifier. The experiment therefore failed the registration criterion.

The likely remaining unknowns are the distinction between Plex's processed machine identifier and the HTTP server identifier, the complete PMS registration/heartbeat lifecycle, and additional server metadata or follow-up calls made by the official Plex Media Server. No further retries should be made without changing one of those tested variables.

## Emulated local flow

PlexBridge was then started as the only server process. A fresh claim token was sent to `POST /myplex/claim?token=...`; the endpoint exchanged it with Plex and returned HTTP `200` with `claimed="1"`. A subsequent `/identity` response also returned `claimed="1"`.

The follow-up account resource lookup still returned no PlexBridge match. This confirms that the local claim emulation works, while Plex-side server publication or registration still requires additional behavior.

## Registration diagnostics

After the emulated claim, Plex exposed a PlexBridge device record through `/api/v2/devices` using the deterministic processed identifier. The device was labeled `Plex Media Server` and `provides=server`, but it had no published connections. Both forms of `/api/v2/server/access_tokens` returned HTTP `403` with error `1080`, and the resource list continued to omit PlexBridge.

This narrows the gap to server-token authorization and connection publication. Plex's Docker bootstrap publishes `customConnections`; PlexBridge now advertises `PLEXBRIDGE_PUBLIC_URL` and sends the PMS-style identity metadata, but a fresh claim with a reachable URL is still required to test that path.
